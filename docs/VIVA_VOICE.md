# Viva workspace commands and voice pilot

## What is implemented

Viva is an opt-in command panel on `/workspace`. Typed commands work without an LLM or microphone. A bounded parser turns English, selected Hindi and Hinglish phrases into an ordered action list. The panel applies those actions through the existing workspace configuration and simulation APIs, records their status in an owner-scoped SQLite audit, and stops on the first failed step. The browser checks the active world ID and revision before each state-changing step; read-only comparison, replay and export keep the world ID check because the simulator can advance its revision when an experiment completes. World edits expose an **Undo last Viva world edit** control, which reloads the prior validated configuration only if the world has not changed since that edit. The audit records **UI action outcomes**, not physical success. The experiment, branches, contacts and replay remain authoritative MuJoCo records.

The tested six-axis request selects the existing UR5e with the modeled parallel gripper, sets high **visual** quality, selects sorting, and starts a real MuJoCo trial. It does not create or qualify a new six-axis controller. The browser designer can create a bounded custom six-revolute-joint arm and parallel-gripper **draft**. It compiles the generated MJCF and measures joint motion in MuJoCo. It cannot yet execute sorting; the UI and API mark it non-executable.

The voice control is disabled unless a dedicated project key and a $5 provider-side monthly project limit are configured. The app requests microphone access only after the visitor presses **Start voice**. Realtime transcription is sent to the same deterministic action parser. The browser uses actual microphone and received output audio spectra for the two signal displays. Idle bars do not animate. The exact action status is printed as a caption; spoken delivery may be generated by the Realtime model, but it cannot update a simulator result.

## API

All routes use the existing `/v1` contract. Every request below requires `X-Workspace-Token`, a random 32–128 character capability generated by the browser. Requests that refer to a session-owned world also need `X-Session-Token`. `Idempotency-Key` is required for command submission and supported for robot draft creation.

| Method | Route | Result |
| --- | --- | --- |
| `POST` | `/v1/agent/requests` | Parse and persist an ordered plan; 201. |
| `GET` | `/v1/agent/requests/{id}` | Owner-scoped plan and step outcomes. |
| `POST` | `/v1/agent/requests/{id}/steps/{index}/outcome` | Persist one action audit in order. |
| `POST` | `/v1/agent/requests/{id}/cancel` | Cancel pending actions. |
| `GET` | `/v1/agent/voice/capabilities` | Whether metered voice is configured. |
| `POST` | `/v1/agent/voice/sessions` | Admit a session and issue a sixty-second ephemeral WebRTC credential. |
| `POST` | `/v1/agent/voice/sessions/{id}/stop` | Close the local admission record. |
| `POST` | `/v1/agent/robot-designs` | Compile and store an owner-scoped six-axis draft. |
| `GET` | `/v1/agent/robot-designs/{id}` | Draft specification and measured compile/control checks. |
| `GET` | `/v1/agent/robot-designs/{id}/model.mjcf` | Download the matching MJCF with the workspace capability. |

Submit example:

```http
POST /v1/agent/requests
X-Workspace-Token: <browser-workspace-capability>
Idempotency-Key: <unique-action-key>
Content-Type: application/json

{"schema_version":"vivacity.agent-request/1.0","utterance":"Hey Viva, make the object heavier, then run the experiment","world_id":"<world-id>","expected_revision":0}
```

The response has `schema_version: "vivacity.agent-plan/1.0"`, `status: "planned"`, and ordered actions. The relative mass action carries `{"multiplier":1.25}`. The client calculates the new mass from the current configuration, asks the workspace API to validate it, loads the resulting world, and then starts MuJoCo. If a bound fails, the step becomes `failed`, the rest remain pending, and the physical world remains unchanged.

An action outcome is reported as:

```http
POST /v1/agent/requests/<id>/steps/0/outcome
X-Workspace-Token: <browser-workspace-capability>
Content-Type: application/json

{"success":true,"message":"Object mass is 0.075 kg in the new physical world."}
```

Do not treat that message as evidence of pickup success. Use `/v1/experiments/{id}`, `/v1/experiments/{id}/branches`, and `/v1/experiments/{id}/replay` for measured results.

## Voice setup and privacy

1. Create a **separate OpenAI API project** for this pilot, configure a $5 monthly project spend limit, and turn on **Enforce a hard limit** in its provider console. A spend alert alone does not stop requests; see the [provider's spend-limit guide](https://developers.openai.com/api/docs/guides/spend-limits). Rotate any key that has appeared in a chat or repository.
2. Set `OPENAI_VOICE_API_KEY` to that project's secret on the backend, and set `VIVACITY_VOICE_PROJECT_LIMIT_USD=5` to attest the provider-side limit. Do not set the key in Vite or the browser.
3. Restart the backend, then verify `GET /v1/agent/voice/capabilities` reports `available: true` using an owner capability.
4. Test an actual microphone session, English/Hindi/Hinglish transcription, interruption, output audio, captions, and usage in the provider dashboard before public release.

The server defaults to `gpt-realtime-2.1-mini` for the Realtime session and `gpt-live-transcribe` for input captions. The browser follows the provider's [ephemeral client-secret](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create), [WebRTC](https://developers.openai.com/api/docs/guides/voice-webrtc), and [server-event](https://developers.openai.com/api/reference/resources/realtime/server-events) contracts. Audio visualization comes from Web Audio analysers of the microphone and received speech streams; the interface does not animate fake waveform data.

The server stops admitting new voice sessions at **$4 in local reservations**: each admission reserves $0.20, with two admissions per owner per hour and twelve per IP per hour. These are abuse and admission controls, **not actual billed-usage accounting**. The provider-side project limit is essential because a browser-held ephemeral credential can consume provider resources after admission, and provider spending controls may lag. The browser closes its WebRTC connection after 90 seconds of inactivity, after three minutes total, or when the panel closes. It sends microphone audio directly to OpenAI; Vivacity stores command text and action outcomes but no audio. Provider handling follows that project's own data policy.

## Validated scope and limits

- Current typed parser supports a bounded vocabulary. Unsupported or ambiguous speech asks for clarification or fails without a world edit. It is not a general assistant and does not execute arbitrary shell, browser, CAD, or model-written code.
- A local path said aloud cannot grant a hosted site filesystem access. The panel requires the visitor to pick a supported file, or a folder containing exactly one supported model file in browsers with [directory-picker support](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker). The existing import page handles mapping and verification. A folder containing several related assets must be packaged as a ZIP and selected as a file. A paired FreeCAD desktop companion is **not implemented**.
- Custom six-axis drafts have compiled collision and inertial geometry plus a motor/gripper specification. The actual task controller, IK, grasp validation and sorting acceptance for new designs are **not implemented**. Existing UR5e sorting uses its separate tested runtime adapter.
- Draft compilation is limited to 30 designs per workspace, 20 attempts per client IP per hour, and 120 attempts globally per hour. These limits bound public MuJoCo compilation work; they are not a substitute for deployment-level admission controls.
- Live OpenAI microphone and expressive output quality have **not been verified** in this branch because no dedicated voice project key with a verified $5 limit was configured. The text path and unavailable-voice fallback have been exercised in a browser.
- `POST /v1/agent/requests` persists an ordered plan; execution currently occurs in the open browser. If the tab closes mid-step, it does not resume the step automatically. The action audit is not a transactional simulator checkpoint.
- The `codex/viva-voice` branch is isolated. It should not replace the current production backend until it is integrated with the current release, a complete post-fix regression run passes, and live voice and spending controls are verified.

## Reproduce locally

From the repository root, use the project Python environment and installed frontend dependencies:

```powershell
$env:VIVACITY_DATABASE='data/viva-voice-local.sqlite3'
$env:VIVACITY_CORS_ORIGINS='http://127.0.0.1:5185'
python -m uvicorn vivacity.api:create_app --factory --host 127.0.0.1 --port 8765
```

In another terminal:

```powershell
cd frontend
$env:VITE_API_BASE_URL='http://127.0.0.1:8765'
npx vite --host 127.0.0.1 --port 5185 --strictPort
npx playwright test --config playwright.viva.config.ts
```

Backend and contract checks:

```powershell
python -m pytest -q tests/test_viva_agent.py
$env:PYTHONPATH='.'; python scripts/export_openapi.py
npm --prefix frontend run generate:api
npm --prefix frontend run build
```

Open `http://127.0.0.1:5185/workspace`, choose **Ask Viva**, and type `Hey Viva, I want a 6 DOF robotic arm, then a high fidelity simulation showing sorting`.
